## North star — what autoinfer is and is not

autoinfer is a **tuning layer**, not a serving layer.

**The thesis (load-bearing claim, intact):**

> Joint three-layer search (L1 engine config × L2 hardware topology ×
> L3 kernel) with a shared substrate (Pareto ledger, cross-layer
> stale-signal invalidation, hybrid LLM+surrogate policy) Pareto-
> dominates per-layer specialist tools (vLLM `auto_tune` at L1,
> NVIDIA Triton Model Analyzer at L1+L2, AutoKernel / KernelAgent at
> L3) on real production model + hardware + workload combinations.

**Operationalised:** for any (model, hardware, SLO, traffic_shape, budget),
autoinfer outputs a deployable recipe (engine config + topology + optional
kernels) that meets the SLO with maximum goodput at the same trial budget
as the best specialist tool at the same layer.

**Three measurable claims the proof program tests:**

| Claim | Measurable definition |
|---|---|
| **Optimality** | autoinfer's recipe ≥ every comparable specialist's recipe at same SLO + budget |
| **Coverage** | Supported matrix spans ≥80% of production inference traffic (Llama / Mistral / DeepSeek / Qwen × H100 / A100 / B200 × chat / batch / code / reasoning) |
| **Reproducibility** | Recipes reproduce on a second machine within ε given full metadata (git SHA, vLLM version, hardware ID, ShareGPT shard sha, seed) |

**autoinfer is NOT:**

- A serving layer (vLLM-router / llm-d / Triton handle that)
- An orchestration layer (KubeRay / KServe handle that)
- A managed inference endpoint service (Together / Anyscale / Fireworks
  occupy that niche; different value-prop — they don't give you the recipe)
- Production-ready today (research-grade; service wrapping is Phase 5)

## T-26c implementation spec (preserved here so the recon survives a branch reset)

**Why T-26c.** C03-S Q2 outcome: L1 surrogate kept-rate was ~20%,
target ≥30%. Diagnosis: surrogate keeps proposing fp8 variants on A100
even after seeing fp8 failures because the failure-region geometry
isn't captured by per-knob weights alone — T-26b's shared
`knob_weights` averages over mixed-kind history, so OOM-region signal
gets diluted by QUALITY_KL-region signal at different knob settings.

**Design.** Per-FailureKind sub-classifiers with per-kind knob weights:

1. Add `kind_weights: dict[FailureKind, dict[str, float]]` field to
   `FeasibilityModel` (already in the dirty file).
2. Refactor `_weighted_vote(self, config, predicate)` to accept an
   optional `knob_weights` parameter:

   ```python
   def _weighted_vote(self, config, predicate, *, knob_weights=None):
       weights = knob_weights if knob_weights is not None else self.knob_weights
       scored = [
           (
               _config_distance(
                   config, obs.config,
                   knob_classes=self.knob_classes,
                   knob_weights=weights,
               ),
               obs,
           )
           for obs in self._history
       ]
       # ... rest unchanged
   ```

3. Add private helper:

   ```python
   def _predict_proba_for_kind(self, config, kind: FailureKind) -> float:
       weights = self.kind_weights.get(kind, self.knob_weights)
       return self._weighted_vote(
           config,
           predicate=lambda o, _k=kind: o.failure_kind == _k,
           knob_weights=weights,
       )
   ```

4. Modify `predict_proba` to dispatch:

   ```python
   def predict_proba(self, config) -> float:
       if len(self._history) < self.min_observations:
           return 1.0
       if not self.kind_weights:
           # T-26b path (backward compat)
           return self._weighted_vote(config, predicate=lambda o: o.success)
       # T-26c path
       max_fail = 0.0
       for kind in FailureKind:
           p_fail = self._predict_proba_for_kind(config, kind)
           if p_fail > max_fail:
               max_fail = p_fail
       return 1.0 - max_fail
   ```

5. `predict_kind_proba` should also route through
   `_predict_proba_for_kind` when `kind_weights` is populated.

**Aggregation choice.** `max_K` (1 − max kind-wise failure probability).
Rationale: kinds are mutually exclusive by construction (`failure_kind`
is either None or a single enum), so `sum_K predict_kind_proba[K] = 1
− predict_proba_aggregate`. With per-kind WEIGHTS, each kind's k-NN
sharpens its in-region signal, so the max kind-wise probability is the
right rejection criterion — a candidate at the OOM-region's heart
gets P(fail OOM) ≈ 1 (sharp), while P(fail of unrelated kinds) ≈ 0.

**Static `derive_kind_weights(catalog)`** in
`src/autoinfer/layers/l1_engine/surface.py`:

```python
def derive_kind_weights(
    catalog: KnobCatalog, *, high_weight: float = 10.0
) -> dict[FailureKind, dict[str, float]]:
    """Build per-FailureKind knob weights. T-26c.

    Static taxonomy of which knobs drive each FailureKind. Future work
    can extend via data-mining from accumulated history (open T-26d).
    """
    KIND_DRIVERS = {
        FailureKind.OOM: {
            "kv_cache_dtype", "gpu_memory_utilization",
            "max_num_seqs", "max_num_batched_tokens", "block_size",
        },
        FailureKind.QUALITY_KL: {
            "quantization", "dtype", "kv_cache_dtype",
        },
        FailureKind.QUALITY_INVARIANCE: {
            "max_num_seqs", "block_size", "enable_chunked_prefill",
        },
    }
    out: dict[FailureKind, dict[str, float]] = {}
    catalog_knob_names = set(catalog.knobs.keys())
    for kind, drivers in KIND_DRIVERS.items():
        weights = {
            name: high_weight
            for name in drivers
            if name in catalog_knob_names
        }
        if weights:
            out[kind] = weights
    # STARTUP failures are catalog-rule violations — use the same
    # rule-mining as derive_knob_weights
    rule_knobs = {rule.when_knob for rule in catalog.constraints}
    rule_knobs |= {rule.requires_knob for rule in catalog.constraints}
    startup_weights = {
        name: high_weight
        for name in catalog.knobs
        if name in rule_knobs
    }
    if startup_weights:
        out[FailureKind.STARTUP] = startup_weights
    return out
```

## Critical invariants the prior session learned the hard way

These are non-negotiable. Violating them produces bad evidence,
incorrect public claims, or wasted budget.

### 1. The strawman trap (the v3 audit lesson)

When measuring kernel speedups, **always include the production
baseline as a comparison column, not just PyTorch unfused**. C03's
first audit (v2) reported "Sonnet's Triton is 2–9× faster than PyTorch
reference" — the v3 audit added `vllm._custom_ops.rms_norm` as a third
column and found Sonnet's Triton is **1.06–1.65× slower** than the
production baseline. The "2–9×" was correct vs unfused PyTorch but
misleading as a production claim.

**Implication for any future kernel-level work (T-31, T-21, T-32):**
the three-way primitive (PyTorch / vllm-native / candidate) is the
right kernel-level audit pattern. The v3 audit script lives at
`/tmp/c03_kernel_audit_v3_filled.py` (artifact); the result is
`basilica-artifacts/campaign03-S-sonnet4-COMPLETED-2026-04-29/kernel_level_audit_v3_three_way.json`.
Bake this primitive into the L3 adapter when T-31 is implemented.

### 2. End-to-end serving is a poor surface for small-op kernel novelty

C03-S's end-to-end paired-control on rmsnorm/silu_mul produced 0/9 NOV
wins (ties within ±0.5%) **not because the kernels were equivalent**
but because rmsnorm is ~3-5% of Qwen3-8B compute and the measurement
noise floor is ±0.5-1%. Even a 5× kernel speedup translates to ~2.5%
end-to-end, well within noise.

**Implication:** for kernel-novelty Q1 questions on small auxiliary
ops, use kernel-level paired-control (T-31), not end-to-end serving.
For end-to-end Q1, target attention (T-21 — ~70% of compute, win
ceiling ~10-25%).

### 3. No fakes, stubs, mocks (CLAUDE.md, global instructions)

Zero tolerance. If something can't be tested / measured, say so
explicitly. The user explicitly cited: "your claims affect SLOs and
SLA contracts and may be used as evidence — you must be 100% accurate
and back every claim with proof."

### 4. Pre-registration discipline (project convention)

No campaign launches without a pre-registration document on `main`.
The pre-reg goes in `docs/research/campaigns/NN-<name>-<date>.md` per
`docs/research/campaigns/TEMPLATE.md`. The "Pre-flight changes" table
must cite real commits — placeholders are a discipline violation.

### 5. No direct push to `main` (project convention)

Every change goes through a feature branch + PR + merge cycle. The
prior session opened ~12 PRs in this arc. Branch naming convention is
`<type>-<scope>-<short-id>`, e.g. `doc-c04-recon-framing-fix`,

### 6. Retraction-style addendum, not silent rewrites

When a prior claim turns out wrong, **add a retraction note + new
section** rather than rewriting the prior text. C03's outcome doc has
this pattern: top retraction note → original (now-retracted) text
preserved → "Q1 corrective audit v2" section → "Q1 corrective audit
v3" section. Every step traceable.

### 7. The harness pieces (`harness/driver.py`, `harness/gate.py`,
`harness/replica.py`) are NOT stubs

replica manages a real `vllm serve` subprocess. Verify the current
state before assuming anything about stub-vs-real boundaries.
